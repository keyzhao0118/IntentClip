# 意图功能矩阵（MVP）

## 1. 目的

Intent 区域不是让模型自由发明工具，而是从产品注册的功能矩阵中推荐 3–5 个候选。每个功能都有稳定 ID、适用信号、执行模板、输出约束和测试集。新增功能必须先进入本矩阵，再允许分类器返回。

## 2. 首发矩阵

| ID | 展示名 | 适用信号 | 默认输出 |
|---|---|---|---|
| `summarize` | 总结要点 | 长段落、文章、会议记录 | 3–7 条要点 |
| `rewrite` | 改写润色 | 草稿、表达生硬、需要调整语气 | 保留原意的完整改写 |
| `translate` | 翻译 | 非首选界面语言或中英混合文本 | 目标语言译文 |
| `explain` | 解释内容 | 术语、报错、代码、复杂概念 | 通俗解释与必要背景 |
| `extract` | 提取信息 | 包含姓名、日期、链接、字段或清单 | 结构化条目 |
| `reply` | 生成回复 | 对话、邮件、请求、通知 | 可直接编辑的回复草稿 |
| `action_items` | 提取待办 | 会议记录、计划、带责任/时间表达 | 待办、负责人、期限 |
| `proofread` | 校对纠错 | 拼写、语法、标点或格式问题 | 修订文本与简短变更说明 |

`explain` 可以针对代码采用代码解释模板，但 MVP 不把“执行代码”作为功能。`extract` 和 `action_items` 分开，是因为后者需要更严格地处理责任人、截止时间和不确定字段。

## 3. 候选排序

分类器接收 Content 和当前功能注册表，只返回功能 ID、排序 score、置信等级与本地化 reason key。规则层随后执行：

1. 丢弃未知、重复和被用户禁用的 ID。
2. 按 score 降序，并应用明显信号修正，例如跨语言文本提升 `translate`。
3. 低置信度时补入 `summarize`、`rewrite`、`explain` 等通用功能。
4. 最终向 UI 提供 3–5 项；UI 不展示 score 百分比。

候选“准确性从高到低”在产品表达上称为“推荐顺序”。未做概率校准前不能写成“92% 准确”。

## 4. 执行契约

- 用户勾选候选即发送 `ExecuteIntent {request_id, content_revision, function_id, options}`。
- `function_id` 必须存在于本地注册表；模型文本不能覆盖系统模板或工具权限。
- 同一面板只允许一个 active function。改选时取消旧请求、清空旧 streaming 状态并展开新 Result。
- 完成结果保留在当前面板内存中，关闭后清除；默认不进入历史。
- 重试沿用同一 Content revision 和 function ID，但生成新的 request ID。

## 5. 功能质量门禁

每个功能至少具备：20 条正常样例、10 条边界样例、5 条中英混合样例、5 条安全样例；明确最大输出、停止条件、低资源表现和错误文案。没有测试集和输出约束的功能不能进入正式矩阵。

## 6. 后续扩展

自定义功能属于 P1。它仍然只能配置提示模板和输出格式，不能直接定义 shell 命令、任意程序启动或网络请求。多选批量执行也属于 P1，需先设计资源排队、结果分组和取消语义。
